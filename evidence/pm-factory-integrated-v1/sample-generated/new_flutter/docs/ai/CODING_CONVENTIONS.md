# اتفاقيات الكود — نمط Flutter + Supabase

## عام
- اللغة في الكود: الإنجليزية (أسماء المتغيرات، الدوال، الملفات).
- اللغة في التعليقات: [عربي / إنجليزي] — وحّد الاختيار عبر المشروع.
- الطول الأقصى للسطر: 100 حرف (يتوافق مع `dart format`).
- التنسيق: `dart format` إلزامي قبل أي commit.
- التحليل الساكن: `flutter analyze` يجب أن يمر بدون تحذيرات قبل الدمج.

## التسمية
- المتغيرات والدوال: camelCase.
- الأصناف (Classes/Widgets): PascalCase.
- الثوابت: lowerCamelCase مع `const`، أو UPPER_SNAKE_CASE للثوابت العامة على مستوى الملف.
- الملفات: snake_case.dart (مطابقة لاسم الصنف الرئيسي بصيغة snake_case).
- المجلدات: snake_case.

## تنظيم الملفات
- كل ملف مسؤولية واحدة — لا تضع أكثر من widget رئيسي واحد في نفس الملف.
- الملف لا يتجاوز [300] سطر دون سبب موثّق.
- الاستيراد مرتب: مكتبات Flutter/Dart → حزم خارجية (pub) → ملفات المشروع الداخلية.

## الـ Widgets
- فضّل `StatelessWidget` ما أمكن؛ استخدم إدارة الحالة المختارة بدل `StatefulWidget` للحالة المعقدة.
- استخرج الـ widgets الكبيرة إلى widgets فرعية بأسماء واضحة بدل دوال `_buildX()` الطويلة.
- لا تُجري نداءات شبكة/قاعدة بيانات مباشرة داخل `build()`.

## معالجة الأخطاء
- لا تُخفِ استثناءات Supabase — التقطها وحوّلها إلى حالة واضحة في الواجهة (خطأ/فارغ/تحميل).
- رسائل الخطأ للمستخدم بالعربية وواضحة؛ رسالة الخطأ التقنية الكاملة تُسجَّل فقط في السجلات.

## الاختبارات
- كل repository أو دالة منطق مهمة لها اختبار وحدة.
- الشاشات الأساسية لها اختبار widget واحد على الأقل.
- أسماء الاختبارات: `should [behavior] when [condition]`.

## Git
- رسائل commit: `type(scope): message` (feat, fix, refactor, docs, test, chore).
- فرع لكل مهمة: `feature/T-XXX-وصف`.

## الممنوعات
- لا `print()` في كود الإنتاج — استخدم logger موحد.
- لا مفاتيح Supabase (خصوصًا service_role) داخل الكود أو الـ repo.
- لا استعلامات SQL خام متكررة يدويًا دون migration موثّق.
