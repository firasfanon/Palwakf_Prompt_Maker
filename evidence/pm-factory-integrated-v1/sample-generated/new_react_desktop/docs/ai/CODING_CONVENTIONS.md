# اتفاقيات الكود — نمط React + Vite + Supabase

## عام
- اللغة في الكود: الإنجليزية.
- اللغة في التعليقات: [عربي / إنجليزي].
- الطول الأقصى للسطر: 100 حرف.
- التنسيق: Prettier + ESLint إلزاميان قبل أي commit.

## التسمية
- المتغيرات والدوال: camelCase.
- الثوابت: UPPER_SNAKE_CASE.
- المكونات (Components) والكلاسات: PascalCase.
- الملفات: PascalCase لملفات المكونات (`UserCard.tsx`)، camelCase للباقي.
- المجلدات: kebab-case.

## تنظيم الملفات
- كل ملف له مسؤولية واحدة.
- لا يزيد الملف عن [300] سطر دون سبب.
- الاستيراد مرتب: مكتبات خارجية → ملفات داخلية (`@/...`) → أنواع.
- استخدم المسارات المطلقة (`@/features/...`) بدل `../../../`.

## الأنواع (Types)
- TypeScript strict mode إلزامي.
- لا تستخدم `any` إلا لضرورة موثقة بتعليق يشرح السبب.
- أنواع جداول Supabase تُولَّد عبر `supabase gen types typescript` ولا تُكتب يدويًا.

## التعامل مع Supabase تحديدًا
- كل استدعاء لـ Supabase يمر عبر طبقة `api/` الخاصة بالميزة — لا نداءات متفرقة داخل المكونات.
- تحقّق دائمًا من وجود RLS على أي جدول جديد تتعامل معه — لا تفترض أن غياب الخطأ يعني وجود الحماية.
- استخدم React Query (أو ما يعادله) لتغليف كل نداء Supabase — لا `useEffect` + `fetch` يدوي متكرر.

## معالجة الأخطاء
- لا تُخفِ الأخطاء.
- رسائل خطأ المستخدم النهائي بالعربية وواضحة؛ لا تُعرض رسالة خطأ Supabase التقنية الخام له.

## الاختبارات
- كل دالة/hook مهم له اختبار وحدة (Vitest).
- كل تدفق أساسي (تسجيل دخول، عملية رئيسية) له اختبار E2E (Playwright).

## Git
- رسائل commit: `type(scope): message` (feat, fix, refactor, docs, test, chore).
- فرع لكل مهمة: `feature/T-XXX-وصف`.

## الممنوعات
- لا `console.log` في كود الإنتاج.
- لا مفتاح `service_role` في أي كود يعمل على المتصفح.
- لا مكتبات جديدة بدون موافقة موثقة في TECH_STACK.md.
